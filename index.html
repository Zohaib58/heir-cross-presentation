01 / Motivation

Why compiled regions?

The original HEIR-generated Python called CROSS public APIs. Simply wrapping that path in jax.jit did not give the desired improvement because array arithmetic remained mixed with Python-side orchestration and metadata handling.

What does JAX actually compile?

JAX traces a Python function containing supported array operations, lowers that computation through XLA, and compiles a reusable executable for the target device. It does not automatically compile arbitrary Python object handling or merge separately compiled calls.

Our goal: expose one connected raw-array function to JAX/XLA, rather than JIT-wrapping the original CROSS public-API orchestration.
01 · ORIGINAL EXECUTION

Public CROSS APIs

Object-oriented operation calls
rotated = ctx.he_rot[level, 1].rotate(ct)
product = ctx.ptct_mul[level].mul(rotated, pt)
result  = ctx.he_add[level].add(product, ct2)

These calls operate on CROSS ciphertext objects. Their surrounding Python can perform evaluator lookup, validations, metadata updates, and wrapper construction.

02 · INITIAL EXPERIMENT

Wrap the existing path in JIT?

Insufficient performance improvement
def original_model(ct, pt, ct2):
    ...  # Public API operations

compiled = jax.jit(original_model)

Simply applying JIT to this Python path did not achieve the desired optimization in our experiments. JAX cannot automatically turn arbitrary Python-side orchestration into efficient fused XLA computation.

03 · ARCHITECTURAL INSIGHT

Expose one raw-array computation

Our compiled-region approach
def raw_region(ct_array, args):
    a = rot._rotate_array(ct_array, ...)
    b = mul._mul_array(a, ...)
    c = add._add_array(b, ...)
    return c

Move reusable preparation and metadata bookkeeping offline. Give JAX/XLA a connected array computation to trace and compile together.

Our approach

Use OutlineCompiledRegions to select connected JaxiteWord operations; generate one raw-array function and separate offline metadata preparation. JAX requires a traceable function, not an MLIR region.

Online measurement boundaries

Warm encrypted computation

Time to execute the already-compiled encrypted neural network, including CPU-to-TPU dispatch and waiting for completion.

  1. Execute encrypted linear layers: rotations, ciphertext–plaintext multiplications, and additions.
  2. Compute square activations and add encrypted-model biases.
  3. Perform required CKKS transformations such as rescaling and relinearization.

Excludes input packing, encryption, decryption, output extraction, and offline preparation/compilation. Native uses mapping._compiled; HEIR uses plan.execute_raw. This is not a device-kernel-only measurement.

Client-to-client online latency

One complete inference request after one-time preparation

  1. Pack input: arrange the input into the encrypted model's required layout.
  2. Encode + encrypt: encode packed values into CKKS slots and encrypt them.
  3. Encrypted forward pass: execute the whole prepared network.
  4. Decrypt: decrypt the encrypted output into plaintext slots.
  5. Extract output: recover the model's output vector from decoded slots.

One-time initialization and compilation are not included. Independently measured per-stage medians are not additive.

Measurement methodology

We measure synchronized host wall-clock latency with Python time.perf_counter()—not CPU execution time or isolated TPU-kernel time.

  1. Start timer
  2. Invoke TPU operation
  3. Wait with block_until_ready()
  4. Stop timer

JAX dispatch is asynchronous, so waiting for completion ensures the timing includes CPU-to-TPU dispatch, TPU computation, and synchronization.

Benchmark protocol: One warmup and three synchronized repetitions per repeated metric; report the median. One-time preparation and compilation are excluded from warm online latency.

XProf: Traces come from separate instrumented profiling runs and do not supply the benchmark latency figures.

Comparison limitations: Different CROSS revisions and arithmetic schedules mean this is a comparison of full execution paths, not a same-revision single-pass ablation. The recorded 128-bit uniform-ternary QP-bit ceiling assessment is met at 32K, not 8K/16K.

Additional setup and comparison controls

Cryptographic settings. Ring-specific integer scale parameters are 1,152,763,181,911,621,633 (8K), 1,152,534,504,430,796,801 (16K), and 1,151,303,352,054,251,521 (32K), all near 260. σ ≈ 3.19; noise multiplier = 1; uniform-ternary secret; Barrett arithmetic; uint32 payloads; JAX x64 enabled.

Matched environment. Separate otherwise matching TPU VMs; same Python, JAX, jaxlib, libtpu, NumPy and SciPy versions, host CPU, memory and kernel.

Workloads. AlexNet-Tiny: input 3 × 16 × 16; LeNet: input 1 × 28 × 28. Both use batch 1, float32 inputs, square activations and four linear + four bias + three square operations. Paired inputs and packaged model weights were checked for correspondence.

Limitations. Native and HEIR use different CROSS revisions, BSGS choices and rescale placement. These timings compare full execution implementations—not an isolated effect of the outlining pass. One warmup + three synchronized repetitions.

Full-Dataset Correctness Validation

We evaluate three implementations:

PlaintextExecute the original neural network without encryption
Native CROSSEncrypt the input, execute Native CROSS inference, and decrypt the output

The objective is implementation correctness.

Dataset preprocessing

Images are provided to the inference implementations as numerical arrays.

LeNet / MNIST

  • Load each grayscale image as a 28 × 28 pixel array.
  • Convert the pixel values to float32.
  • Scale pixel values by dividing by 255.
  • Normalize with mean 0.1307 and standard deviation 0.3081.
  • Produce an input tensor of shape 1 × 1 × 28 × 28.

AlexNet-Tiny / CIFAR-10

  • Load each RGB image as a 32 × 32 × 3 array.
  • Scale the float32 pixel values by dividing by 255.
  • Normalize the three channels using means (0.4914, 0.4822, 0.4465) and standard deviations (0.2023, 0.1994, 0.2010).
  • Apply 2 × 2 average pooling with stride 2 before encryption.
  • Produce an input tensor of shape 1 × 3 × 16 × 16.

The exact same normalized image values are used for all three inference paths.

3. Experimental Workflow

For each model and CKKS ring configuration:

  1. Load the trained network and dataset. Reuse the model weights from the original benchmark.
  2. Preprocess the input images. Apply the appropriate dataset normalization and model-specific transformations.
  3. Prepare encrypted execution once. Initialize the cryptographic resources and prepared/compiled execution paths. Reuse them across the entire dataset.
  4. Execute the three inference paths. Run plaintext inference, Native CROSS encrypted inference, and HEIR Prepared encrypted inference on the same inputs.
  5. Decrypt encrypted outputs. Recover the output logits from Native CROSS and HEIR.
  6. Compare predictions and numerical outputs. Calculate accuracy, prediction agreement, logit differences, and execution failures.

Each input image is encrypted separately for each encrypted path. The three implementation phases execute in separate processes.

4. Correctness Metrics

Every model produces ten output logits per image, one for each class.

The predicted class is the index of the maximum logit: ŷ = argmaxk∈{0,…,9} zk

We evaluate four complementary correctness metrics.

4.1 Classification Accuracy

Measures how often the predicted class matches the ground-truth label.

Accuracy = (Correct predictions / Total test images) × 100%

We calculate this separately for plaintext, Native CROSS, and HEIR Prepared.

Interpretation: Accuracy measures the predictive performance of the neural network, not whether two implementations behave identically.

4.2 Prediction Agreement

Measures whether two implementations produce the same predicted class for the same image, regardless of whether the prediction is correct.

Agreement(A,B) = (Matching predictions / Successfully compared images) × 100%

We evaluate three pairs:

  • Plaintext vs. Native CROSS
  • Plaintext vs. HEIR Prepared
  • Native CROSS vs. HEIR Prepared

Two implementations can achieve identical classification accuracy while making different mistakes. Therefore, equal accuracy alone does not establish prediction equivalence.

A 100% three-way agreement means that all three implementations predict the same class for every successfully evaluated image, including identical incorrect predictions.

4.3 Numerical Consistency

Matching predicted classes does not imply identical numerical outputs.

For corresponding output logits, we calculate the absolute difference:

ei,k = |zi,kNative − zi,kHEIR|

Here, i identifies the test image and k identifies the output class.

We report:

Maximum absolute logit difference

emax = maxi,k ei,k

Mean absolute logit difference

emean = [Σi=1…M Σk=0…9 ei,k] / (10M)

where M is the number of successfully compared image pairs.

For 10,000 successfully compared images, these metrics cover 100,000 output logits.

Small numerical differences can occur without changing the predicted class. Numerical comparison therefore provides evidence beyond classification agreement.

4.4 Execution Reliability

For each implementation, record:

  • Total images attempted
  • Successful inferences
  • Failed inferences
  • Invalid or nonfinite output logits

Failed inferences count against classification accuracy. Prediction agreement and logit differences are calculated on successful pairs, with the compared-image count reported separately.
